# 技术决策记录

## 记录格式

### 2026-06-28 - 初始化 Agent 工作规范
- 决策：建立 `AGENTS.md`、`docs/` 和 `checklists/` 作为长期项目协作规范。
- 原因：让后续任务遵循按需检索、逐步执行、自检更新的流程。
- 影响范围：项目文档、任务执行流程、后续 Agent 协作方式。

### 2026-06-28 - 当前阶段只建立项目治理文档
- 决策：本阶段仅初始化项目文档、任务体系、检查清单和 `AGENTS.md`，不编写业务代码，不锁定技术栈。
- 原因：先固定产品问题、协作边界和可验证流程，避免技术选型早于需求澄清。
- 影响范围：仓库当前只包含 Markdown 文档；后续代码或依赖引入必须由新任务明确授权。
- 状态：已被后续工程实施替代；仓库现已完成阶段1、阶段2和阶段3A，本条仅保留初始化历史。

### 2026-06-28 - 采用事件主线与共享记录的概念模型
- 决策：以事件承载装修事实的时间主线；账目、施工问题、尺寸、决策、采购、调研和待办作为可关联领域记录；时间线、账本、问题看板和空间档案作为共享数据的多种投影视图。
- 原因：同一装修事实往往同时影响时间、费用、空间和行动项，共享记录可减少重复录入与视图冲突。
- 影响范围：后续需求拆分、数据建模、识别流程和界面设计。
- 状态：概念决策已确认并已在阶段2落地；具体字段和关系以当前领域模型与API契约为准。

### 2026-06-28 - 自动识别采用人在回路原则
- 决策：系统自动生成的是可追溯的候选记录，用户可调整AI自动补全的类型与字段、追加手工记录并确认所选；低置信度推断不得伪装成已确认事实。
- 原因：装修信息包含金额、质量问题和重要决策，错误自动入账或错误归档的代价较高。
- 影响范围：识别结果模型、交互流程、审计信息和验收标准。
- 状态：当前交互已由2026-06-30“录入方案收敛与阶段3B重构”决策更新。

### 2026-06-28 - 首版产品与部署边界
- 决策：首版为个人私用的响应式Web/PWA；Windows本地自托管，通过私有组网HTTPS访问，不开放公网注册和端口。
- 原因：兼顾电脑整理、手机现场录入、个人隐私和运维可控性。
- 影响范围：客户端形态、鉴权、部署、离线能力和安全测试。

### 2026-06-28 - 技术规划基线
- 决策：前端采用React、TypeScript和Vite PWA，后端采用Python与FastAPI，结构化数据采用SQLite，附件保存到本地文件目录。
- 原因：适合响应式交互、本地单用户部署、Python AI生态及低运维成本。
- 影响范围：后续应用骨架、接口、存储、测试和部署任务。
- 状态：技术栈已落地；当前版本以依赖清单为准，涉及库用法、配置或升级时继续按项目规则通过Context7核对。

### 2026-06-28 - 八类记录浅覆盖与共享实体
- 决策：首版覆盖事件、账目、施工问题、尺寸、决策、采购、调研和待办；空间、商家、材料、附件和项目阶段作为共享实体。
- 原因：真实样本证明一次描述会跨多种分类，而材料和空间会被多类记录复用。
- 影响范围：领域模型、AI提取协议、接口和页面导航。

### 2026-06-28 - 施工扩展表达方式
- 决策：施工进度、里程碑和验收测试先作为事件子类型；空间拆改由事件、决策和空间关联表达；材料不新增顶层记录类型。
- 原因：满足当前样本表达，同时避免在样本不足时过早增加顶层分类。
- 影响范围：事件类型、空间档案、材料档案和后续样本验证。

### 2026-06-28 - 采购与账目分离
- 决策：采购记录订单总额、商品和履约；账目记录每笔实际资金流；余额通过关联计算。
- 原因：样本001同时存在1100元订单和500元预付款，二者语义不同。
- 影响范围：账本、采购跟踪、金额计算和接口契约。

### 2026-06-28 - 即时预览与待确认箱
- 决策：AI提取后先展示即时预览，用户可立即确认或稍后在待确认箱处理；离线只能保存草稿。
- 原因：在低录入负担和事实准确性之间取得平衡。
- 影响范围：采集流程、候选状态、PWA离线边界和确认事务。
- **状态：已撤销（2026-06-29）**。用户确认过程中发现待确认箱/稍后处理实际使用率为零，简化为一键确认流程，删除整个待确认箱功能。

### 2026-06-28 - 可插拔AI与持久化识别任务
- 决策：使用统一AI适配协议；云端适配器显式启用；图片和OCR使用持久化任务与独立worker。
- 原因：便于切换云端/本地模型，避免供应商锁定，并保证耗时识别任务可重试。
- 影响范围：隐私、任务状态、模型评测和错误恢复。

### 2026-06-28 - 跨模型Agent采用单写者串行
- 决策：不建立固定多Agent团队；DeepSeek、Kimi、GPT等模型可轮流接手，但同一时刻只有`tasks/ACTIVE.md`中的Agent可以写入。
- 原因：减少上下文断裂、文件冲突和不同模型同时修改同一项目的风险。
- 影响范围：AGENTS规范、任务锁、交接记录和审查流程。

### 2026-06-28 - 本地数据与附件策略
- 决策：所有运行数据固定放在项目根目录`.local-data/`；原始附件支持JPG/JPEG、PNG、WebP、HEIC和PDF，单文件上限50 MB，原件长期保留；备份规划为每日一次并保留30天。
- 原因：避免SQLite、附件和模型散落到系统盘，同时维持原始事实可追溯。
- 影响范围：SQLite、附件、模型、备份、导出、Git忽略和后续上传校验。
- 状态：目录约定和附件上传（含SHA-256校验）已实现；自动备份尚未实现。同硬盘无法防硬盘损坏的风险已由用户接受。

### 2026-06-28 - 首个MVP工程基线
- 决策：使用专用Conda `homebuild-log` Python 3.13环境；前端采用React 19、TypeScript 6、Vite 8和Vitest 4，后端采用FastAPI 0.128、SQLAlchemy 2、Alembic和pytest。
- 原因：隔离项目依赖，并建立可启动、可迁移、可测试的最小纵向骨架。
- 影响范围：`frontend/`、`backend/`、依赖锁定、测试和Windows本地运行命令。
- 状态：已实施；Vite由8.0.10升级到8.1.0以修复npm审计报告的Windows路径安全问题。

### 2026-06-28 - Bearer Token 单用户认证
- 决策：采用 HS256 JWT Bearer Token 作为认证方案；密码使用 Python 内置 hashlib PBKDF2-HMAC-SHA256 哈希（600,000 次迭代），不引入 passlib 或 argon2-cffi 等第三方密码库。
- 原因：单用户本地场景不需要 OAuth2 复杂度；使用标准库内置哈希减少依赖。
- 影响范围：`app/auth.py`、`app/core/config.py`、全局认证中间件、前端登录页。
- 状态：已实施；后端 12 项测试 + 前端 6 项测试通过。

### 2026-06-28 - SourceEntry / Attachment 数据入口
- 决策：以 SourceEntry（原始文字输入）和 Attachment（文件上传 + SHA-256 去重）作为系统数据入口，先保存原始内容再进入后续识别流程。
- 原因：人在回路原则要求原始事实不可被 AI 结果覆盖；同步建立文件去重和完整性校验机制。
- 影响范围：`app/models.py`、Alembic 迁移 0002、`app/api/sources.py`、前端录入表单。
- 状态：已实施；后端 9 项测试通过。

### 2026-06-28 - 审计日志

- 原因：装修涉及金额和决策，需要可追溯的操作日志；审计本身不提供修改或删除接口以保证完整性。
- 影响范围：`app/audit.py`、`app/api/audit.py`、Alembic 迁移 0003。

### 2026-06-28 - 阶段 2B 采用服务端只读投影
- 决策：时间线、账本、问题看板、空间档案和基础搜索由服务端集中投影现有正式记录；前端不复制金额和空间聚合规则，也不创建视图事实副本。
- 原因：同一事实需要跨视图一致，金额待付、未知时间和父子空间聚合必须只有一套可测试语义。
- 影响范围：新增五个只读查询接口、统一详情、审计目标过滤和响应式核心导航；不新增业务表或迁移。
- 状态：已实施并通过自动化、浏览器检查与用户亲自验收。

### 2026-06-29 - CandidateBundle单表支撑待确认箱
- 决策：每次成功提取创建不可静默覆盖的`CandidateBundle`版本；待确认箱直接查询候选包中的`deferred`项，不另建`pending_confirmations`副本表。
- 原因：避免候选正文和暂存副本产生同步分叉；同一份候选可同时承担编辑、暂存、确认、版本冲突和审计语义。
- 影响范围：迁移0006/0007、候选API、跨来源确认事务和前端待确认箱。
- **状态：已撤销部分（2026-06-29）**。`CandidateBundle`单表模型保留，但待确认箱/稍后处理/`deferred`状态不再由前端使用；确认流程简化为单一「确认所选」按钮。

### 2026-06-29 - 删除待确认流程与三按钮精简
- 决策：删除「待确认」导航页、「稍后处理」、「一键确认全部明确项」、「保存候选修改」四个功能；保留单个「确认所选」按钮；全部未确认条目默认勾选。
- 原因：用户实际使用中从未使用稍后处理/待确认箱，三按钮带来额外认知负担。编辑后的 payload 随「确认所选」直接提交，不再需要草稿保存中间态。
- 影响范围：删除 PendingBox 组件、`PATCH /candidate-bundles/{id}` 和三个 pending-confirmations 后端端点、清理 5 个前端文件、3 个测试文件；`deferred` 不再表示“稍后处理”，自 2026-07-01 起仅作为候选被用户移除后的持久化隐藏状态。
- 状态：已实施；lint + 前端 17 项测试通过。

### 2026-06-29 - AI 候选字段兜底补全
- 决策：AI 返回的候选记录可能存在必填字段缺失（如 Decision 缺 topic），后端不做 422 拒绝，而是通过 `_fill_missing_required` 根据 record_type 自动补全合理默认值（topic→summary，phenomenon→summary 等），同时更新系统 prompt 逐类列出必填字段清单。
- 原因：候选记录不等于正式记录，始终需人工确认；用默认值补全不影响追溯性，避免因 AI 漏字段阻断用户录入流程。
- 影响范围：`app/api/extractions.py`（_fill_missing_required）、`app/ai_adapter.py`（SYSTEM_PROMPT）、`app/api/domain.py`（校验错误中文化）。
- 状态：已实施；小主浏览器亲验通过。

### 2026-06-29 - 手工录入与共享档案安全删除
- 决策：手工表单使用按记录类型变化的示例占位文字；空间和共享档案只允许物理删除未被子空间或正式记录引用的误建项目，删除前由前端二次确认并由后端再次校验。
- 原因：空白表单、内部关系枚举和缺少删除入口增加了使用成本；自动解除引用会损伤装修历史，不能为了删除便利破坏追溯性。
- 影响范围：领域删除API、录入工作区、记录详情、审计、测试与使用说明；正式记录仍只支持归档，底层记录关系与核心视图计算保持不变。
- 状态：已实施；无需数据库迁移。

### 2026-06-29 - 默认根房屋与记录状态按类型解释
- 决策：默认项目至少保留一个根房屋“整套房屋”；缺失根房屋的旧库升级时自动创建并接纳无上级的非房屋空间。记录状态展示按记录类型解释，决策`pending`为“待确认”，待办`pending`为“待处理”。
- 原因：首个房间没有上级可选会迫使用户理解并手工搭建根节点；单一全局状态翻译会把不同业务含义混成同一个词。
- 影响范围：迁移0008、空间删除约束、录入与详情状态文案、材料品牌表单及相关测试文档；数据库状态枚举和材料表结构不变。
- 状态：已实施。

### 2026-07-01 - 问题与待办业务时间统一到日期
- 决策：问题的预计/实际解决日期与待办的截止/实际完成日期统一使用`YYYY-MM-DD`，不记录时分秒；系统创建、更新和审计时间继续保留精确时间。

### 2026-07-01 - 问题与待办分工及详情统一维护
- 决策：施工问题保存缺陷、处理方案、处理人、预计与实际解决日期；待办保存具体动作、执行人、截止与完成日期。二者通过记录关系连接，不合并为同一类型。
- 决策：录入页移除“已保存的记录”重复维护区，正式记录的修改和删除统一放在各视图右侧详情中。
- 决策：问题首次进入已解决/已关闭时自动记录实际解决日期，重新打开时清空；用户可在详情中修正。
- 决策：候选卡片的“移除”写入 `deferred` 状态，确认其余候选后不得重新出现；该状态不恢复待确认箱或稍后处理入口。
- 原因：问题是需要追踪的对象，待办是执行动作；统一详情入口可避免同一记录在录入页和查询页出现两套维护体验。
- 影响范围：问题详情字段、迁移0012、候选移除接口、录入界面、记录详情和测试。

- 决策：所有数据库日期时间统一写为无偏移UTC、读取为aware UTC，API返回带时区ISO 8601，前端固定按`Asia/Shanghai`展示。来源录入时间与事情发生时间独立，未知发生时间显示“待补充”。

- 影响范围：迁移0009、来源/候选/记录引用模型、来源维护与复核API、核心详情和录入工作台。
