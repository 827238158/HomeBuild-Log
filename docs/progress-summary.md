## 一、这个项目要做什么

装修过程中，大量零散信息散落在聊天记录、手机相册和脑子里。HomeBuild Log 的目标是：你像聊天一样描述发生了什么，系统自动帮你整理成——

- **时间线**：装修到哪一步了，哪天做了什么
- **账本**：花了多少钱、还要付多少
- **问题看板**：有哪些施工问题、处理了没
- **空间档案**：每个房间用了什么材料、做了哪些决定

首版是个人私用的本地 Web 系统，所有数据在你自己电脑上，不经过任何云端。

## 三、关键设计逻辑

### 3.1 为什么先本地规则后 AI

本地规则（`local-rule-v1`）不联网，每次保存来源后即时生成中文建议，明确项默认勾选、你不确定的不选，核对修改后一次确认。

三个意图：① 阶段 3 之前已有可用体验，不依赖任何 AI 供应商；② 未来 AI 结果可跟本地规则交叉校验；③ 断网时本地规则作为兜底。AI 只生成候选，最终确认由你手动完成——装修涉及金额和决策，不能让机器替你做主。

### 3.2 为什么一事多记录

一句"今天去光彩定了花砖，付了 500 预付款"同时包含事件、采购、账目。系统允许一条来源同时产生多条不同类型记录，互不覆盖。这是"视图不是副本"的前提——时间线、账本、看板从同一个事实池读取各自需要的部分，不复制数据。

### 3.3 为什么公共 records 表 + 八张详情表

所有记录共享的字段（标题、空间、来源、创建时间）集中在公共 `records` 表；每类记录特有的字段（如账目的 `direction`、采购的 `total_amount`）放在各自的详情表。好处：公共字段查询只需扫一张表，不需要跨八张表做 UNION；同时避免了把所有字段塞进一张宽表导致的空字段膨胀。

### 3.4 为什么共享实体单独建表

空间、材料、商家、装修阶段会被多种记录类型复用。例如"卫生间花砖"同时出现在采购（商品）、尺寸（规格对象）、决策（选择内容）中。如果每种记录各自存名称，改一处名要改多处；集中为共享实体后，多类记录通过 ID 引用，修改一处全局生效。

### 3.5 为什么阶段 1 按 A→B→C→D 顺序

阶段 1 的目标是"一个能跑起来的本地系统骨架"。按依赖关系拆成 3 步子任务：

```
A. 单用户会话         登录/认证
        ↓  【没有登录，后面的接口全是裸奔，所以必须先做】
B. 来源与附件         文字录入 + 文件上传
        ↓  【数据从哪来？这是整个系统的唯一入口，所有后续功能都从这里读数据】
C. 审计记录           自动操作日志
        ↓  【数据有了之后，每次增改都必须留痕，装修金额和决策需要可追溯】
D. 导出恢复           已跳过至阶段 5
```

每步在上一步可运行的基础上增加能力，做完一步验证一步。

## 五、启动后实际能做什么

打开两个终端，分别启动后端和前端：

```bash
# 终端 1：后端
cd backend
D:\Anaconda\envs\homebuild-log\python.exe -m fastapi dev app/main.py --host 127.0.0.1 --port 8000

# 终端 2：前端
cd frontend
npm run dev
```

浏览器访问 `http://127.0.0.1:5173`，体验流程：

```
┌───────────────────────────────────────────────────────────────────┐
│ 1. 后端控制台打印管理员密码（如 a1b2c3d4...）                    │
│ 2. 密码输入框 → 登录 → 进入主页（显示"本地服务运行正常"）        │
│ 3. 文本框中输入"今天去看了瓷砖"，点保存                           │
│    下方出现中文建议卡片：明确项自动勾选，你核对修改后一次确认     │
│ 4. "最近记录"显示刚保存的内容 + 时间戳                            │
│ 5. 点开来源，可在高级区手工拆分八类记录、维护空间和记录关系       │
│ 6. 数据在 .local-data/db/homebuild-log.sqlite3 中可查             │
│ 7. 不登录直接访问任何 API → 401 拒绝                             │
│ 8. 每条创建操作都自动写入审计日志（GET /api/v1/audit 可查）      │
└───────────────────────────────────────────────────────────────────┘
```

## 六、下一步：阶段 2B 核心视图与基础搜索

### 2A 回顾

阶段 2A 已落地八类记录（事件/账目/施工问题/尺寸/决策/采购/调研/待办）、共享实体（空间/材料/商家/装修阶段）、记录关系（derived_from / pays_for / resolves 等 9 种）。7 条真实装修样本已通过验证，数据模型足够支撑**字段级别**的记录。

**但当前只能通过 API 和表单增删改查，缺少图形化的全景浏览——这正是阶段 2B 要解决的问题。**

### 四个视图的详细规划

| 视图 | 展示什么 | 数据来源 | 验收标准 |
|------|----------|----------|----------|
| **时间线** | 按日期排列事件，聚合关联的决策、账目、待办作为展开标签 | `records`（type=event）+ `record_relations` | 7 条样本的事件按日期排列，关联记录正确展开 |
| **问题看板** | 按状态列（发现/处理中/等待/已解决/已关闭）分组的施工问题卡 | `records`（type=issue）+ `issue_details.status` | 7 条样本的问题出现在正确状态列，拖动可改变状态 |
| **账本** | 流水视图 + 采购视图 + 摘要卡（总采购额/已付/待付） | `records`（type=ledger_entry / procurement）+ 关联计算 | 7 条样本的 500 元预付款和 1100 元订单显示一致，待付金额正确 |
| **空间档案** | 房屋→房间→局部构件的层级列表，每个节点展示相关记录摘要 | `spaces` 层级 + `record_relations` 聚合 | 7 条样本中"卫生间淋浴区"能展开看到花砖采购和花色决策 |

### 推荐开发顺序

```
时间线 ──→ 问题看板 ──→ 账本 ──→ 空间档案 + 基础搜索
  ①           ②           ③               ④
```

- **① 时间线首选**：数据依赖最少，基本是 `records` 表按时排序，最直观，做出来就能用
- **② 问题看板**：复用时间线的记录查询基础设施，新增看板状态列分组
- **③ 账本**：涉及采购与账目的跨表金额计算（已付 = 关联 LedgerEntry 汇总），逻辑最复杂，放在中间攻坚
- **④ 空间档案 + 搜索**：空间层级遍历需要递归查询，搜索是跨表全文检索，适合最后攻坚

每个视图完工后立即用 7 条样本核对一致性——时间线里展开某采购能看到金额，账本里同一采购的已付/待付必须相符。

### 阶段 2B 不做什么

- ❌ 不引入任何 AI 能力（AI 是阶段 3 的事）
- ❌ 不修改已有领域模型（2A 已验证字段够用）
- ❌ 不破坏已有的建议确认流程（2A 的录入体验保持不变）
- ❌ 不实现第三方图表库、交互户型图或 PDF 导出等高级可视化

### 2B 之后的远景

阶段 2B 完成后，你将看到完整的"手工记录 + 视图浏览"闭环。此后各阶段定位：

- **阶段 3**：AI 介入文字提取——输入文字后 AI 生成候选（仍是建议，需你确认），替代当前的本地规则。本地规则保留为校验和断网兜底
- **阶段 4**：支持手机拍照上传票据，PWA 离线保存草稿，Tailscale 私有 HTTPS 访问
- **阶段 5**：搜索优化、批量导入导出、每日备份与恢复演练，确保长期数据安全可维护

## 七、方向确认

以下 5 条是整个项目不能动摇的基线，请确认是否仍然成立：

1. **本地优先**：所有数据在 `.local-data/`，不经过任何云端
2. **单用户私用**：没有多账户，没有权限体系
3. **AI 可选**：AI 只生成候选建议，最终确认必须由你手动完成
4. **一事多记录**：一条原始描述可以同时产生事件、账目、决策等多种记录
5. **原始事实不覆盖**：你的原始文字和图片永远不会被 AI 结果静默替换

上述基线保持不变。当前处于阶段 2A/2B 交界，下一项候选任务是阶段 2B 核心视图与基础搜索。
